# Project、Assets、Web 重构规划

> 状态：方案和第五节的决定已确认（2026-10-23），按三部分依次实施。第 4–9 版按六轮评审补全了保存冲突、并发、快照、导出记录、素材的身份、库的目录、备份和恢复，以及验收。第 10 版（2026-10-24）做减法：去掉为进程中途退出专门加的记录、锁和状态，改成固定的先后加重跑，残余情况写明边界；第 7 条决定改为只警告。第 6 版起素材库的数据库叫 `catalog.db`。现状以 main（96e1b87）为准。
> 不考虑历史兼容：旧数据不迁移，旧命令不留别名，不加格式版本号。

## 〇、为什么要做

Valle 首个开源版本（2026-09-07）就带着三样东西：一个集中存放的项目修订库，一个全局素材库，以及包括 Studio、Console 和一个只能播放的预览页在内的几个网页。之后一个半月里，Motion、Timeline、渲染和 Studio 编辑器都大改过（时钟、能力规划、性能），这三样却基本没动。

- **工作流已经变成直接改文件。** agent 写 `.motion.tsx` 和 Timeline JSON，`timeline studio` 直接编辑 JSON 文件。项目修订库那套"提交整份文档、带 base revision、处理 staleBase"的数据库式设计，在这种工作流里用处不大，反而多了一圈导出和提交。
- **素材库和项目、渲染之间没有通路。** 它用内容哈希当 ID，人和 agent 都不好用；分析功能和后来的 media 工具重复，还有从没接上的功能。
- **Web 端是一步步长出来的。** Studio、Console、Preview 三个页面挂在同一个本地服务器上，哪个能用取决于是哪条命令启动的。

剪辑软件都是从"一个项目"开始的。这次重构先把项目立为起点，再把素材库重做成跨项目复用的素材收藏，最后把 Web 收成一个 Studio。顺序固定：先 Project，再 Assets，最后 Web 页面，后一部分依赖前一部分。

## 总原则

1. **CLI 是 agent 的主界面。** 每个操作都有命令。Studio 给人看和微调，后做；它和命令共用同一套原语和校验，可以把原语组合成一次交互。
2. **文件即真相。** 项目和素材库都是普通文件夹，Timeline、组件、媒体都是文件，agent 用普通的文件工具就能读写。唯一的例外是素材库的标签和备注，它们存在库里的 SQLite 数据库中。
3. **一个概念只有一个名字、一个位置。**
4. **只做原语。** 便利功能由 agent 组合，Valle 不内置编排。例如不内置 VLM 批处理。
5. **不考虑历史兼容。** 旧格式、旧目录、旧命令直接删除。
6. **不过度设计。** 每部分末尾都列出"暂不做"。进程中途退出和并发写入，只靠原子写入、SQLite 事务、固定的先后和可以重跑的命令来处理；剩下的少数残余情况写明边界，不再为它们加专门的机制。

## 给 agent 的统一约定

project 和 assets 的命令都遵守以下约定：

| 约定 | 内容 |
| --- | --- |
| 命令形状 | `valle <领域> <动词>`，和 motion、timeline、media 一样 |
| 输出 | `--json` 只输出一个结果。`--events` 输出进度，最后给一个 report。成功时是 `status: "ok"` 加结果字段；失败时是统一的 `error`，包含 code、message 和 hint。一次处理多个文件的命令逐项返回结果：全部成功是 `ok`，有失败时是 `partial`，退出码非零 |
| 路径 | 项目内的路径一律相对项目根，只有项目外的引用才用绝对路径。素材库里的素材用库内路径称呼，比如 `music/upbeat.mp3`。任何命令都不使用哈希 ID |
| 找项目 | 从当前目录向上找 `project.json`，也可以用 `-C DIR` 指定 |
| 幂等 | 重复执行结果一致：重复 add 返回已有的文件，没变化的 save 返回 unchanged，同样的备注不重复加。命令中途失败（包括进程被杀）后，重跑同一条命令即可；只有素材库的 edit 和 remove 要先用 show 看现状，因为上次可能已经做完 |
| 重名 | project 和 assets 用同一套规则：内容相同就返回已有的那份；名字相同、内容不同就自动加后缀（`-2`、`-3`），结果里标明改过名；明确指定的名字（`--name`、改名、移动）撞名时报错。判断重名一律不区分大小写 |
| 并发 | 项目里 Valle 自己的写入只在操作期间加项目锁，不会覆盖没看到的改动；素材库靠 SQLite 事务和不覆盖已有文件的写入。agent 直接改项目文件时 Valle 拦不住，所以 Studio 开着时，改文件前先重读 |
| 不交互 | 命令不会停下来询问。有风险的操作有兜底：restore 之前先存一个快照，要覆盖的每个文件都在里面；素材库删除的文件进系统废纸篓 |
| 错误提示 | hint 给出下一条可以直接执行的命令 |
| 不依赖 Studio | 所有原语都有对应命令，Studio 里的组合操作用几条命令也能完成。Studio 开着时，agent 在外面改了文件，Studio 会自动重载 |

## 一、Project 重构

### 来龙去脉

项目修订库是首个版本的设计：
- 项目存在 `$VALLE_HOME/projects/<id>/`。
- 每次修改都提交一整份 Timeline，并带上 base revision，结果分为 committed、unchanged、staleBase、rejected 四种。
- 为了防止并发写，还有一个单进程的 owner 锁。

它面向的是"多个编辑者并发修改同一份文档"的场景。实际用下来：

- agent 本来直接写文件，修订库却要求先 `show` 导出，改完再 `apply` 提交，多了一圈。
- 项目里只存 Timeline 这一份 JSON。`create` 和 `apply` 会把相对路径改成绝对路径，组件和媒体都留在原处，所以项目不自包含，换个目录就断。
- 版本只覆盖 Timeline，组件源码的修改不在历史里。
- Studio 为它单独维护了一种 project 会话，保存和冲突的语义都和文件模式不同。

### 现状

| 方面 | 现状 |
| --- | --- |
| 存储 | `$VALLE_HOME/projects/<id>/`，包含 HEAD 和 `revisions/N/`（timeline.json、canonical.json、revision.json） |
| 命令 | create、show、apply、history、restore、render、studio。参数是项目 ID，不是路径 |
| 修改方式 | 提交整份文档并带 base revision；restore 会追加一个新修订 |
| 并发 | 单进程 owner 锁，进程不退出就一直不释放 |
| 路径 | 提交时把相对的资源路径改成绝对路径 |
| 渲染 | 用磁盘上当前的文件重新编译。存下来的 canonical.json 不参与渲染 |
| Studio | 有独立的 project 会话。另有文件模式（`timeline studio FILE`），直接编辑 JSON 文件 |
| Timeline 的保存（文件模式） | 有自己的保存协议：基线版本号（进程内计数，不落盘）；保存时先核对浏览器预览时用的组件和素材摘要，写入前再读磁盘核对一次；结果分为 committed、unchanged、staleBase、rejected 四种。名字和修订库的一样，但不依赖修订库 |
| 源码的保存 | Studio 保存组件源码是另一套协议：按打开时的内容摘要（baseDigest）比对，写入前再读磁盘核对一次；结果分为 saved、unchanged、conflict、changedAfterWrite 四种。只在进程内互斥 |
| 导出的输入 | 视频和音频边复制到临时目录边算摘要，复制前后各核对一次文件身份；组件源码和其它资源读进内存。渲染读的是这些副本 |
| 文件身份 | Unix 上是大小、修改时间、设备号加 inode 和 ctime；Windows 上是大小、修改时间、卷号加文件 ID，没有 ctime。能发现大小和修改时间都不变的替换，有专门的测试，因为替换会换新的文件号。Windows 上原地改写、大小不变、又改回修改时间的情况发现不了，Studio 的预览缓存也受影响 |
| 成片的写出 | 先写成目标旁边的 `.valle-part-*` 暂存文件，发布时不覆盖已有文件；发布失败会撤回自己已经发布的文件。进程被杀时暂存文件会留下 |
| 路径校验 | resources 的值一律按 URL 校验：本地路径不能有空格，带冒号的相对路径（比如 `media/12:30.mp4`）会被当成协议名拒掉。编译、渲染、组件素材绑定和 Studio 都不需要这个限制 |
| 无人调用的代码 | Studio 文档会话（StudioDocumentSession） |
| 规模 | 修订库源码约 2k 行、测试约 1.4k 行；CLI 项目命令约 500 行；另有两组只为修订库存在的 CLI 测试 |

### 规划

**项目就是一个普通文件夹**，建在当前目录（也就是 agent 的工作区），不再放进 `~/.valle`：

```
promo/
├── project.json        {"name": "promo", "timeline": "timeline.json"}
├── timeline.json       入口 Timeline；画布尺寸和帧率只写在这里
├── components/         Motion 组件（.motion.tsx）：画面、转场、特效、字幕样式都是组件
├── media/              组件以外导入的文件：视频、音频、图片、字体、数据等
├── renders/            导出结果
└── .valle/history/     快照
```

- `project.json` 只有两项：项目名和入口 Timeline。
- 上面的目录只是默认约定，Timeline 引用任何路径都可以。Timeline 里的相对路径照旧从 Timeline 文件所在的目录算起；入口 Timeline 在项目根目录，所以就是相对项目根。
- 目录名 `components/` 和 Timeline 里引用 Motion 的 `component` 字段一致，素材库也用同一个名字。
- 本地路径可以带空格和冒号：Timeline 的路径校验改成只有带 `协议://` 的值才按 URL 校验（见取舍）。所以 `add` 保留原文件名。

**命令**：沿用现有的动词 create、show、history、restore、render、studio，新增 add、check、save，删除 apply。

| 命令 | 作用 | `--json` 结果 |
| --- | --- | --- |
| `valle project create DIR [--width W --height H --fps F]` | 建目录骨架和一条空 Timeline，默认 1920×1080、30 fps。DIR 可以是已有的文件夹，里面已有的文件不会被覆盖；已经是项目时报错，hint 提示用 `show` | 项目根目录和新建的文件 |
| `valle project show` | 项目概况 | 项目名、画布、时长、轨道、媒体、项目外引用、快照数、最近一次导出 |
| `valle project add FILE… [--link]` | 把文件放进项目：`.motion.tsx` 进 `components/`，其它进 `media/`。同一个卷上用克隆，几乎不占空间；重名按统一约定处理。素材库里的素材直接给完整路径即可（素材库的搜索结果里有）。加 `--link` 则不复制，直接引用原文件。带相对 import 的组件报错，见下面的"导入组件"；多个文件时允许部分成功，见"批量 add" | 逐项返回每个文件的别名和路径，正好是一条可以原样写进 `resources` 的条目（`--link` 时路径是原文件的绝对路径）。别名避开 Timeline 里已经用过的，只用 ASCII 字母、数字和 `. _ -`，文件名里没有可用字符时按类型起，比如 `audio`、`audio-2`。另有类型、媒体信息（时长、尺寸、帧率、有无音轨），以及是否已经存在、是否改过名 |
| `valle project check` | 对入口 Timeline 做 `timeline check`，再列出项目外引用和缺失的文件 | 警告和错误 |
| `valle project render [-o PATH] [--frame/--frames/--storyboard] …` | 等同于 `timeline render`。不给 `-o` 时写到 `renders/`，文件名带快照号，撞名时加后缀，不覆盖已有文件。完整导出会自动存快照，每次导出写一条导出记录 | 导出信息和快照号 |
| `valle project save [-m MSG]` | 存一个快照 | 快照号；没有变化时返回 unchanged 和已有的快照号 |
| `valle project history` | 列出所有快照 | 快照号、时间、说明、来源（save、render 或 restore） |
| `valle project restore N` | 先存一个恢复前的快照，再恢复到 N，规则见下面的"恢复" | 恢复到的快照、恢复前的快照，以及没有写回的文件：和 N 记录不一致的二进制文件、项目外的文件、符号链接 |
| `valle project studio` | 用 Studio 打开项目。这一部分只用文件模式打开入口 Timeline，顶栏显示项目名；首页和项目面板留到第三部分 | 地址 |

`add` 不改 `timeline.json`。它只返回路径和建议别名，由 agent 自己写进 `resources`。

**导入组件**：组件只能 import `./`、`../` 开头的 TS 模块，路径从组件所在的目录算起，越出这个目录就报错，所以一个组件用到哪些文件是确定的。
- `add` 先在原位置用编译器的同一套解析读出组件的 import。
- 除了 `valle` 还 import 了别的文件，就报错并列出这些文件，一个都不复制；hint 给出把它们按原来的相对位置复制进 `components/` 的命令。解析失败也报错。
- 素材库的 `add` 用同一条规则。自己复制进来的多文件组件照常能用，快照也会捕获它的 import。

**批量 add**：`project add` 和 `assets add` 一次可以处理多个文件（素材库还可以是整个目录），这时允许部分成功。现在的 `assets add` 就是这样做的，这里把它写成契约。
- 命令级的错误（参数不对、不在项目里）整体报错，什么都不做。
- 单个文件出错只影响它自己：每个文件的复制都是原子的，前面成功的留下。
- 结果逐项返回：新增、已存在、改了名，或失败及原因。全部成功是 `ok`，有失败时是 `partial`，退出码非零。
- 重跑时，成功过的文件按内容返回已有的那份，只重试失败的。

**文件身份**：快照的摘要缓存、导出时对媒体的复核、素材库的扫描和 Studio 的预览缓存，都沿用现有的同一套检查判断文件变没变，这次不改。它在 Windows 上的已知限制见现状，以后单独修。导出记录里的摘要不受影响，因为捕获时每个字节都算过摘要。

**快照**：存的是项目实际用到的输入，也就是渲染时捕获的那一份，不是"所有文本文件"。
- 复制：`project.json`、入口 Timeline、它引用的组件和组件的相对 import、数据和着色器文件。
- 只记内容摘要：视频、音频、图片、字体、3D 模型和环境贴图。按类型区分，不判断是不是文本。摘要按文件身份缓存，身份变了才重算。
- Motion 只允许相对路径 import，所以这个范围是封闭的：`.git/`、依赖目录、临时文件、`renders/`、`.valle/` 都不会进快照，不需要排除清单。
- 项目外引用的文件同样捕获：源码复制进快照，记下原路径；媒体只记摘要。
- 算不出范围时（比如 Timeline 坏了），save 报错，hint 给出 `valle project check`。restore 照常能用，见下面的"恢复"。
- 没被引用的草稿不进快照。要保存项目里的全部文件，用 git。

**恢复**
- 持项目锁，先存一个恢复前的快照，再把快照 N 里的文件逐个写回去，每个文件都是原子写入。
- 恢复前的快照 = 当前用到的输入 + N 里每个要写回的文件。后者记下现在的内容，文件不存在就记"不存在"。所以不管当前 Timeline 能不能算出范围，恢复覆盖的每个文件，原来的内容都在这个快照里。例如 N 引用 `a.motion.tsx`，当前 Timeline 已经改用 `b.motion.tsx`，之后又改过的 `a.motion.tsx` 照样会先存下来。
- 只写项目目录里的普通文件：不跟随符号链接，不写项目外的文件，不动二进制文件。这几类只报告和快照记录不一致的地方。
- 快照之后新增的文件不删，恢复后它们只是没被引用。"不存在"的记录只用来报告，恢复到这个快照时也不删文件。
- 中途失败（进程被杀、断电）时，一部分文件已经恢复。重跑同一条 `restore` 即可；原来的内容在第一次存的那个恢复前快照里，`history` 里能看到。

**导出记录**
- 完整导出只捕获一次输入，直接用现有的捕获：视频和音频冻结成临时副本并算出摘要，组件源码和其它资源读进内存。渲染读的是这份副本，快照也用这同一份捕获，不再另读磁盘。所以成片和导出记录一致是捕获本身保证的。
- 每次完整导出写一条记录，有自己的导出 ID，存在对应快照的 `exports/` 下。同一个快照可以有多条：不同的编码、尺寸，或者同时进行的几次导出。内容没变时复用快照，往里加一条记录即可。
- 记录里有：输出路径和摘要、全部输入的摘要和文件身份、实际的导出参数（范围、编码、尺寸、帧率等）和 Valle 版本；导出期间用到的媒体变了，也记下警告。
- 顺序沿用现有的暂存和不覆盖发布：
  1. 持项目锁捕获输入，存或复用快照；
  2. 不持锁渲染到目标旁边的暂存文件，不会挡住 Studio 保存；
  3. 再比一次用到的媒体原文件（包括项目外的），先比文件身份，身份变了再比摘要。变了就在结果里给出警告，成片照常交付，因为它用的是冻结的副本，本身没错；
  4. 写导出记录，再把暂存文件改名成最终文件，不覆盖已有文件。发布失败就删掉这条记录。
- 先写记录再发布，所以交付出去的成片一定有记录。中途失败时快照照样保留，它就是导出开始时的源码，重跑即可。边界：进程正好在写完记录、发布之前被杀，会留下一条找不到成片的记录；被杀时留下的暂存文件和现在一样，可以直接删掉。
- 这保证**可追溯**：总能说清一个成片用的是哪些字节。能不能**完整复现**，取决于这些媒体文件还在而且没变；恢复到这个快照时，会报告哪些已经变了。

**并发**：一个 agent 加一个人，就是两个写入者。
- 去掉常驻的 owner 锁。Valle 自己的写入（Studio 保存、add、save、restore、导出时存快照）只在操作期间持有项目锁 `.valle/lock`，进程退出时系统自动释放。
- 写入前按摘要比对。Timeline 和源码各自沿用现有的保存协议，写入时共用项目锁：Timeline 看到的不是最新内容就返回 staleBase，预览用的组件或素材变了就返回 rejected；源码和打开时的摘要对不上就返回 conflict。都不会覆盖自己没看到的改动。
- 锁主要保护多文件操作。没有它，restore 写到一半时 Studio 保存了一个组件，就会被 restore 覆盖。
- 所有写入都先写临时文件再改名，读的一方不会读到半份文件。
- agent 用自己的工具直接改文件时，Valle 能发现（Studio 自动重载或提示冲突），但拦不住它拿旧内容覆盖别人的改动。所以 agent skill 要求：Studio 开着时，改文件前先重读。另外，最后一次比对和改名之间还有极短的空档，外部写入正好落在这里时检测不到，这是普通文件系统的上限。

**删除**
- 持久修订库：修订库代码及其测试、持久的修订号和提交协议、owner 锁、`~/.valle/projects`、每个修订里的 canonical.json、Studio 文档会话。
- Studio 相关：服务器和 Studio 前端里的 project 会话、Console 的项目面板。
- 测试：两组只为修订库存在的 CLI 测试，以及 CI 清单里对应的条目。
- 旧项目不迁移。

**保留**：两套保存协议原样保留，一套是 Timeline 的（基线版本号、两次摘要核对、四种结果），一套是源码的（baseDigest、写入前再核对、四种结果）。项目 Studio 直接用它们，只在写入时加上项目锁。这一部分不改协议。

同时重写 project 文档、CLI 文档、timeline 文档里的路径规则，以及 agent skill 里关于项目的部分。

### 取舍

- **用文件夹，不用集中存储。**
  - 好处：看得见、能移动、能打包，也能直接进 git（忽略 `.valle/` 和 `renders/` 即可），agent 用普通文件工具就能操作。
  - 代价：没有全局列表了（第三部分用"最近项目"补上）；写入也不再由一个进程统一把关。agent 和 Studio 就是两个写入者：Valle 自己的写入靠操作期间的项目锁加摘要比对来保护，agent 直接改文件的那一侧只能检测、不能阻止（见上面的并发）。
- **快照整份复制用到的源文件，不做修订日志，也不内置 git。** 源文件都是小文本，整份复制最简单，恢复时也不依赖任何工具。不做 diff 和分支，需要的话直接在项目目录里用 git。
- **快照范围按"用到的输入"算，不按"所有文本文件"算。** 不需要排除清单和文本判定，也和导出记录对得上。代价是没被引用的草稿不进快照，要全量保存就用 git。
- **二进制文件不进快照。** 媒体文件大，按不可变的输入对待，只记摘要。代价是：如果有人覆盖了 `media/` 里的文件，旧快照无法恢复它原来的字节，只能报告"不一致"。所以导出记录保证可追溯，不保证可完整复现。
- **完整导出自动存快照。** 导出、快照和导出记录用同一份捕获，所以每个交付出去的视频都能对应到确切的源文件。内容没变就复用上一个快照，不会刷出一堆。单帧和 storyboard 属于预览，不存快照。
- **导出期间媒体变了只警告，不报错。** 成片和记录用的都是导出开始时冻结的副本，本身是对的。报错只能多保证一件事：交付时项目里还留着原样的媒体，为此却要在发布前持锁复核，中断后还要收尾。代价是这样的成片以后可能无法从项目完整复现，警告会写进结果和导出记录。
- **`add` 默认复制。** 项目自包含，移动、打包都不会断。同一个卷上用克隆，几乎不占空间：克隆出来的是独立文件，删掉或修改源文件都不影响项目里的副本，只是删掉源文件后空间不会释放，因为副本还在用；跨卷或者文件系统不支持克隆时，自动改成普通复制。放在别的盘上的大素材用 `--link`，这时才依赖原文件，`check` 会把它列为项目外引用。
- **`add` 不改 Timeline。** Timeline 归 agent 管，Valle 不在背后改它。代价是 agent 要多做一步：自己写 `resources`。
- **多文件组件先报错，不一起导入。** 依赖范围虽然确定，但几个组件各自带的同名辅助文件会冲突，改名又得改写 import，而 Valle 不在背后改源码。代价是这类组件要按 hint 手工复制一次。
- **恢复前的备份按"要覆盖的文件"补全，不按"所有文件"。** 被覆盖的文件一定有备份，范围仍然很小；没被覆盖的文件本来就还在磁盘上。
- **每次导出单独一条记录，先写记录再发布。** 交付出去的成片一定有对应的记录，不需要中间状态，也不需要收尾。代价是进程正好在两步之间被杀时，会多出一条找不到成片的记录。
- **删除 apply 和持久修订号。** agent 直接改文件，比"导出、修改、提交"少一圈。Studio 保存的冲突检测沿用现有的两套协议。
- **目录叫 `media/`，不叫 `resources/` 或 `assets/`。** `resources` 是 Timeline 的别名表，还指向组件、项目外的文件和 URL，目录用这个名字会让人以为所有资源都在里面。`assets/` 和全局素材库 `valle assets` 同名，agent 容易误用 `valle assets add` 往项目里加文件。剪辑软件普遍把导入的素材叫 media，字体、数据也放在这里。
- **放宽 Timeline 的路径校验（会改变现有行为）。** 现在 resources 的值一律按 URL 校验，可下游并不需要这个限制，而 macOS 默认的截屏、录屏文件名和 iCloud 云盘的路径都带空格。改成只有带 `协议://` 的值按 URL 校验，本地路径只拒控制字符。别名的规则不变。

### 暂不做

- 管理一个项目里的多条 Timeline（其它 Timeline 照样能用 `timeline render` 渲染；在 Studio 里打开它们时没有历史和导出面板）
- 项目模板
- 快照的 diff 和分支
- 把项目外的文件收集进项目（collect）
- 用 `add` 导入多文件组件（现在报错，见"导入组件"）
- Windows 上的原地改写检测（没有 ctime，见现状的"文件身份"）

## 二、Assets 重构

### 来龙去脉

素材库同样是首个版本的设计，按一套完整的媒体资产管理系统来做：
- 文件按内容哈希存放，用 sha256 摘要当 ID；
- 元数据、带时间的批注、实体（人物、地点、产品及其别名），加一个 SQLite 全文索引和只读 SQL；
- 一套分析流水线：自带的镜头检测和节拍检测、外部 VLM、一个预留给 ASR 的槽位；
- 一套 pin/lease 机制，用来保护"固定渲染包"用到的文件。

此后，media 工具作为独立的"文件进、文件出"工具发展起来。Timeline 和 Motion 一直用路径引用资源，固定渲染包的命令也始终没有上线。结果素材库成了一个挂在旁边的索引：
- 哈希 ID 人和 agent 都不好用，在 Finder 里也看不出哪个文件是什么；
- 分析功能和 media 工具重复；
- 还有几条接不上的死路径。

素材库真正要做的事其实很明确：把字体、音乐、音效、视频、图片、3D、组件这些可以复用的素材放在一起，打上标签、写上备注，让人和 agent 都能很快找到，再放进项目里用。

这次就按这个目标重做：保留真正有用的基础，也就是 SQLite 全文搜索和带时间的备注，去掉过度设计的部分。

### 现状

| 方面 | 现状 |
| --- | --- |
| 存储 | `$VALLE_HOME/assets`：文件按内容哈希存放；每个哈希另有一份元数据、分析结果、批注和实体；另有一个 SQLite 全文索引（支持中文），它只是投影：结构版本对不上时删掉所有表，再从每个哈希的元数据重建 |
| 身份 | 素材用 `sha256:…` 摘要当 ID，命令里要抄这串哈希 |
| 命令 | `valle assets` 下有 14 个子命令 |
| 和项目、渲染的关系 | Timeline、Motion 和渲染都不读素材库。agent 要先 `resolve` 拿到路径，再自己抄进 `resources` 或 `--asset` |
| 转写 | `assets transcript` 读的槽位没有任何东西会写入：既没有 ASR 分析器，也没有导入命令 |
| 镜头 | 有两套检测：库里自带的帧差检测，以及 `media shots` 的模型检测。两者结果格式不同，文档还专门提醒不要混用 |
| 节拍 | 素材库里有一套，Motion 的音频分析里另有一套 |
| VLM | 专用的外部命令协议，外加一个 sidecar 服务；预算按人民币分计算；默认模型参数写死在代码里 |
| pin/lease | 只有测试会创建，但每次删除和清理都要查它们。约 0.9k 行源码、1k 行测试 |
| 其它死代码 | component 类型（为已经删除的 Lottie/HTML 组件服务）；Console 里一段只有测试在用的桥接代码 |
| 不一致 | 结果格式是 `{ok, data, error}`。时间范围写成 `--range 1 3`，而 media 写成 `1,3`。导入有 reflink、copy、reference 三种模式。主目录只认 HOME，Windows 上得手动设置 VALLE_HOME |
| 缓存 | 渲染的 URL 下载缓存在 `~/.cache/valle/assets`，名字和素材库撞车；缩略图和帧在 `~/.valle/cache` |
| Web | 只有 `project studio` 会挂上素材库。Console 没有入口，文档里也没提 |
| 规模 | 素材库源码约 7.4k 行（含 pin/lease）、测试约 3.6k 行，CLI 约 1.3k 行 |

### 规划

**定位**：素材库是跨项目复用的素材收藏。下面三个概念各管一层：

| 概念 | 是什么 | 用在哪里 |
| --- | --- | --- |
| 项目文件 | 项目 `media/` 和 `components/` 里的文件，Timeline 用相对路径引用 | 当前这个视频 |
| 素材库 | 可以复用的素材，带标签和备注，可以搜索 | 跨项目复用 |
| Motion `asset://` | 组件的参数槽位，用 `--asset` 或在 Timeline 里绑定 | 单个组件（这次不动） |

**目录和类型**

```
~/.valle/assets/
├── .valle/         Valle 自己的文件：catalog.db、备份和临时文件
├── fonts/
├── music/
├── sfx/
├── videos/
├── images/
├── 3d/             3D 模型和环境贴图
├── shaders/
├── components/     .motion.tsx
├── data/           JSON、CSV
└── other/
```

- **类型由文件本身决定。** Valle 按内容和扩展名识别以下类型：视频、音频、图片、字体、3D 模型、环境贴图、着色器、组件、数据，认不出的归为 other。类型只有两个用处：
  - 筛选；
  - 决定怎么用：探测哪些媒体信息，放进项目时进 `components/` 还是 `media/`。
- **目录由用户组织。**
  - `add` 不指定目录时，按类型放进上面的默认目录。音乐和音效都是音频，默认进 `music/`，音效用 `--to sfx/`。
  - 加 `--to` 可以放到任何地方，比如 `--to brand/acme/`；也可以在 Finder 里自己建目录、挪文件。
  - Valle 不给目录名赋予含义，目录用到时才建。
- **素材用库内路径称呼**，比如 `music/upbeat.mp3`、`components/lower-third.motion.tsx`。数据库内部另有稳定的 ID，见下面的"素材的身份"。
- **其它类型照样能存。** LUT、PSD、字幕文件之类会归为 other：能打标签、写备注、搜索，也能复制进项目，只是 Valle 不能直接渲染。以后 Valle 支持了新类型，识别清单里加一项，库里已有的文件下次扫描时自动识别，不需要迁移。

**管理目录**：Valle 自己的文件都放在库根目录的 `.valle/` 里，和项目的 `.valle/` 是同一个约定。
- 里面有 `catalog.db`（连同 SQLite 的 `-wal`、`-shm` 文件）、`backups/`，以及导入时用的 `tmp/`：文件先复制到这里，再改名到位，扫描不会读到复制到一半的文件。进程被杀时留在 `tmp/` 里的文件可以直接删。
- 扫描跳过库根目录的 `.valle/`，也跳过所有以 `.` 开头的文件和目录，比如 `.DS_Store`。其余位置都可以放素材，子目录里叫 `catalog.db` 的文件也只是一个普通素材。
- 换机器时复制整个库文件夹，`.valle/` 一起带走。

**素材的身份**：对外用库内路径称呼素材；数据库内部每条素材有一个稳定的 `asset_id`，标签和备注都关联它，它不出现在命令和结果里。路径、内容哈希和文件身份都只是这条素材的属性：
- 改名和移动只改路径，`asset_id` 不变，标签和备注跟着走。
- 同样内容的几份文件是几条素材，各有自己的 `asset_id`。
- 路径上换成了别的文件：`remove` 先删条目再删文件，之后放到这个路径上的文件是一条新素材；在 Finder 里直接覆盖，算这条素材的内容改了，和覆盖保存一样。想当成新素材，就先 `remove` 再 `add`。

**文件夹管文件，catalog.db 管标签和备注**
- 每次使用前快速扫一遍目录：
  - 新放进来的文件自动入库（识别类型、探测媒体信息）；
  - 在 Finder 里改过名或移动过的文件，认回原来的标签和备注：先找文件号和内容都相同的缺失条目，再找内容唯一对应的。改名和移动不改变文件号，复制会换一个新的，所以有重复内容也分得清；
  - 不见了的文件不删标签和备注，只标成缺失，`list` 和 `search` 默认不显示；同样内容的文件回来时自动认回。只有 `remove` 才真正删除。
- Finder 里复制出来的重复文件各算一条素材，去重只在 `add` 时做。上面两条都对不上时就当新文件。
- 扫描按路径比对文件身份（和项目用的是同一套检查，见第一部分的"文件身份"），只有新文件和身份变了的文件才读内容，所以几千个文件也很快。
- 内容哈希只在内部用：导入时判断库里是否已经有同样的文件，以及上面这种认回。它不出现在任何命令和结果里。

**catalog.db 的数据安全**：标签和备注只存在 `catalog.db` 里，它是主数据，不再是可以随手重建的索引。删掉它，扫描只能恢复媒体信息，恢复不了人写的东西。
- 表分两类：用户数据（素材条目、标签、备注）永不自动删除；派生数据（媒体信息、全文索引）随时可以从文件和用户数据重建，结构变了就直接重建。
- 结构对不上或数据库损坏时，命令报错停下，hint 给出 `valle assets recover`。绝不自动删表，也不新建空库。
- 备份：每天第一次写入前，用 SQLite 的备份接口在 `.valle/backups/` 里存一份，按日期命名，保留最近 7 份；`remove --missing` 这类批量删除之前也先存一份。数据库很小，7 份几乎不占空间。
- 恢复用 `valle assets recover`。它不打开当前的数据库，所以当前的库打不开时，照样能列出和换回备份。
  - 不带参数：列出备份（日期、素材数、备注数），打不开的备份标成损坏。
  - 带上备份名：先把当前的 `catalog.db` 连同 `-wal`、`-shm` 原样移到 `.valle/backups/replaced-<时间>/`，不对它做任何 SQLite 操作，所以不依赖它还能读；再把备份复制到位，做完整性检查；最后照常扫描一次。用命令而不是手工复制，是因为手工复制容易把旧的 `-wal` 套到换回来的数据库上。中途失败就重跑同一条命令。
  - 被换下来的数据库不计入 7 份，也不自动删除，`recover` 同样能列出和换回它。
  - 限制：换库时不要开着 Studio，也不要同时跑别的素材库命令。备份之后同一路径上换过文件的，恢复后的扫描按"在 Finder 里覆盖"处理，旧备注会挂到新文件上，需要时手动删掉。
- 边界：只能找回最近 7 份备份里的状态，更早误删的备注找不回。要更长的历史，就自己备份整个库文件夹。
- 数据库的写入都走 SQLite 事务，多个 agent 同时写不会丢数据。
- 换机器时复制整个文件夹即可，复制时不要有命令在写。到了新机器上文件号都会变，第一次扫描会把内容重读一遍。

**文件和数据库的先后**：SQLite 事务管不到文件的复制、改名和进废纸篓，所以先后是固定的。中途退出时留下的状态，都和在 Finder 里新增、改名的结果一样，下次扫描本来就会处理：
- `add`：先把文件放到位（经过 `tmp/`，不覆盖已有文件），再在一个事务里写条目、标签和备注。中途退出时，文件会被扫描当成新文件入库，只是没有这次的标签和备注；重跑同一条 `add` 会按内容找到它，把标签和备注补上。
- `edit`：先改名或移动文件，再更新条目。中途退出时，扫描会按文件号和内容把文件认回原来的条目，结果和做完一样。
- `remove`：先在一个事务里删掉条目和它的标签、备注，再把文件移进废纸篓。中途退出时文件还在，扫描把它当成一条没有备注的新素材，再 `remove` 一次即可。旧备注已经删了，不会挂到之后放到这个路径上的文件上。
- `tag` 和 `annotate` 只改数据库，一个事务就够了。

**命令**：沿用现有动词。

| 命令 | 作用 |
| --- | --- |
| `valle assets add FILE\|DIR… [--to DIR] [--tag T]… [--note TEXT] [--name N]` | 复制进库（同一个卷上用克隆，几乎不占空间），默认按类型放进对应目录。加的是目录时，保留它的子目录结构，比如整个音效包。同样内容已在库里时，直接返回已有的那份，并把这次的标签和备注合并上去，所以重跑是安全的。带相对 import 的组件报错，规则和 `project add` 相同。多个文件时允许部分成功，规则见第一部分的"批量 add"。`--name` 只用于单个文件 |
| `valle assets list [DIR] [--kind K] [--tag T] [--missing]` | 列出素材，可以只看某个目录；`--missing` 只看缺失的条目 |
| `valle assets search TEXT [--kind K] [--in DIR] [--tag T] [--filter …]` | 全文搜索并排序，范围是名字、目录、标签、备注和字体名；`--filter` 按时长、横竖屏筛选 |
| `valle assets show PATH` | 单个素材的详情：类型、媒体信息、标签、备注 |
| `valle assets edit PATH [--name N] [--to DIR]` | 改名或移动 |
| `valle assets tag PATH [--add T]… [--rm T]…` | 改标签 |
| `valle assets annotate PATH [--at T \| --range START,END] --text TEXT` | 写备注，可以带时间点或时间段，比如在 45 秒处记"进高潮"；`--id` 替换、`--rm` 删除已有的备注。同一个素材上文字和时间都相同的备注只存一条 |
| `valle assets remove PATH\|--missing` | 删除素材：文件进系统废纸篓，标签和备注一起删。`--missing` 清理所有缺失的条目 |
| `valle assets recover [BACKUP]` | 不打开当前的数据库，库坏了也能用。不带参数时列出备份；带上备份名，就把数据库换回这一份，规则见上面的"恢复" |
| `valle assets sql QUERY` | 只读 SQL，方便 agent 做临时查询 |

备注只有文字和可选的时间，不再带标签和实体；标签只打在素材上。

**重名**（规则和项目一致）
- **内容相同**：不管叫什么名字、放在哪个目录，都不再复制，直接返回库里已有的那份。同一个素材想归到多个分类，靠打标签，不存两份。
- **名字相同、内容不同**：自动加后缀。`music/upbeat.mp3` 已经存在时，新文件存成 `music/upbeat-2.mp3`，结果里返回实际路径并标明改过名。想自己起名就用 `--name`。
- **明确指定的名字撞名**（`--name`、改名、移动）：直接报错，不自动改名，hint 提示换一个名字。
- **不同目录下同名**：不算重名。搜索结果都带完整的库内路径，能区分开。
- **只差大小写**：判断重名一律不区分大小写，各个平台表现一致。
- **两个 agent 同时添加同名文件**：不会互相覆盖。写入时只在文件不存在时才创建，后到的自动加后缀。
- **导入整个目录**：保留子目录结构。音效包里同名的文件各在各的子目录里，大部分重名自然就没有了。

**和项目的关系**
- 搜索结果里同时带着素材的库内路径和完整路径。
- 把完整路径交给 `project add`，素材就复制进项目：组件进 `components/`，其它进 `media/`。
- 项目里放的是副本，库里改了或删了都不影响项目。
- 备注不带进项目。备注是用来找素材、选片段的：agent 读到"45 秒进高潮"，自己换算成 `trimStart` 之类的参数；人在 Studio 里预览库里的素材时也能看到。

**其它改动**
- **删除**：
  - 命令：resolve（素材就是路径，不需要再解析）、stats（数量在 list 的结果里）、transcript、analyze 和 entity。
  - 存储和身份：sha256 ID 和按哈希存放；每个哈希一份的元数据文件（并进 `catalog.db`，所以它成了主数据，见上面的数据安全）；结构版本对不上就删表重建的逻辑，只对派生数据保留。
  - 实体（用标签代替）；标题（就用文件名）。
  - 内置分析：镜头、节拍、VLM、预算，以及那个没人写入的转写槽位。
  - pin/lease，以及只有测试在用的固定渲染包命令。
  - 导入方式：引用外部文件，以及三种导入模式。
  - maintenance 那一组命令（verify、reindex、gc），改为每次使用时自动对齐。
  - 旧的 component 类型（现在的组件指 `.motion.tsx`）。
  - Console 里的桥接代码。
- **和 CLI 对齐**：
  - 结果格式和其它命令一致。
  - 时间范围统一写成 `--range START,END`。
  - 主目录只用一种解析方式：先看 VALLE_HOME，再看 HOME 或 USERPROFILE。素材库、最近项目和缓存都用它。
- **缓存收拢到 `~/.valle/cache/`**：缩略图、波形、URL 下载各占一个子目录，`VALLE_CACHE_DIR` 仍可覆盖。渲染的 URL 下载缓存不再叫 assets。模型权重的位置不变。
- **旧库不迁移**：如果 `~/.valle/assets` 还是旧格式（还有旧的 `index.db`，或者按哈希存放的文件），命令直接报错，提示先把它移走。

**agent 的典型用法**

```sh
valle assets add whoosh.wav --to sfx/ --tag 转场 --note "短促的风声" --json
valle assets annotate music/upbeat.mp3 --at 45 --text "进高潮" --json
valle assets search 风声 --kind audio --json             # 结果：库内路径、完整路径、标签、备注、时长
valle project add ~/.valle/assets/sfx/whoosh.wav --json   # 复制进项目 media/，返回路径和建议别名
```

### 取舍

- **保留素材库，不只用普通文件夹。** 复用的前提是找得到。几千个音效、几百首音乐，光靠文件名找不到，需要标签、备注和能处理中文的全文搜索。
- **文件夹加 SQLite，不用哈希式存储，也不用单个 JSON。**
  - 按类型分的目录，人在 Finder 里看得懂，agent 看路径就知道是什么。
  - SQLite 负责搜索、排序和并发写入，几千上万个文件也不慢。
  - 单个 JSON 做不了中文分词，两个 agent 同时写还会丢数据。
  - 代价是 catalog.db 成了主数据，必须有备份，而且不能再自动删表。
- **对外用库内路径称呼素材，不用哈希；内部用 `asset_id`。** 路径好认，也好写；内部 ID 让改名、路径被新文件占用、同内容的多份都有清楚的含义。代价是改名或移动后对外的路径就变了：Valle 会按文件号和内容认回标签和备注，agent 重新搜一次即可。
- **Valle 的文件集中放进 `.valle/`，不和素材并列。** 扫描只需要跳过一个目录，和项目的约定一样，备份和临时文件也有了固定位置。代价是数据库藏了起来，要找它得知道这个目录。
- **备份保留 7 份，不做无限历史。** 能找回最近几天误删的备注，所占空间可以忽略；更久的历史交给用户自己备份库文件夹。
- **从备份恢复后照常扫描，不另设规则。** 备份是几天前的状态，这期间同一路径上换过文件的，旧备注会挂到新文件上。这种情况很少，备注也还在，改掉或删掉即可。另设保守规则，又会把备份之后在 Finder 里覆盖保存过的素材拆成一条缺失加一条新素材，还得保证它抢在常规扫描之前跑。
- **中途退出靠固定的先后和扫描收拾，不留操作记录。** 先后定死之后，中途退出留下的状态都是扫描本来就会处理的，不需要额外的表、锁和收尾。代价是 edit 和 remove 不能盲目重跑，上次可能已经做完，要先用 show 看一眼。Finder 里的改名和移动按文件号和内容认回，代价是在 exFAT 这类文件号不稳定的文件系统上，遇到重复内容可能认不回，这时按新文件处理，备注留在缺失的条目上。素材库默认在主目录，很少碰到。
- **导入时重名自动加后缀，不报错。** 批量导入不会因为一个重名就整体中断，结果里写明实际路径。只有明确指定的名字（`--name`、改名、移动）撞名时才报错。
- **项目只放副本，不引用库里的文件。** 项目自包含。代价是改进了库里的组件之后，已有项目不会自动更新，需要的话重新 add。
- **类型和目录分开。** 类型清单只对应 Valle 能用的资源，目录完全由用户决定。所以存什么都行，以后支持新类型也不用迁移。
- **保留带时间的备注，去掉实体。** 音乐的高潮、视频里的某个镜头需要时间点；人物、产品这类命名，用标签就够了。
- **缺失的文件保留备注。** Finder 里误删、移出去再移回来，都不会丢备注。代价是缺失的条目会累积，要用 `remove --missing` 清理。
- **备注不带进项目。** 项目只放文件，继续不依赖素材库。代价是 Studio 里的片段上看不到库里的备注，要看就在素材面板里预览。
- **不再内置分析（能力减少）。** 素材库只管存和找，转写、镜头等分析由 media 工具对文件来做，每种分析只有一个实现。具体会少掉三样：
  - VLM 批处理；
  - 免模型的镜头检测；
  - 素材库里的节拍检测。Motion 的音频分析里还有一份节拍检测，以后需要时再作为 media 工具开放出来。
- **不支持引用外部文件。** 素材库是一个自包含的文件夹。放在别的盘上的大素材，直接在项目里用 `--link`。
- **名字不改。** 仍叫 `valle assets`。Motion 的 `--asset` 是把一个素材绑进组件的参数，两者本来就是同一个概念。

### 暂不做

- 把转写、镜头等分析结果放进素材库（以后要做，也是导入 media 工具的结果）
- 把素材库的备注带进项目、显示成片段上的标记（要先定义备注存在项目的哪里，以及裁切、变速、循环之后时间怎么换算）
- 多文件组件（组件要用的图片和字体，通过 `asset://` 参数由 Timeline 绑定）
- 向量检索
- 反查某个素材被哪些项目使用
- 素材库的同步和共享

## 三、Web 页面重构

### 来龙去脉

Web 端是一步步长出来的：
- 首个版本：Studio 剪辑器、管理素材和项目的 Console，以及一个只能播放的预览页。
- 9 月中旬：Studio 改版，开始支持直接编辑 Timeline 文件；播放、编译、导出收拢成引擎 SDK。
- 10 月：Studio 的界面又改过一次。

三条 `studio` 命令启动的是同一个本地服务器，只是带的上下文不同，页面之间一直没有整合过。

### 现状

| 页面 | 地址 | 是什么 | 实际情况 |
| --- | --- | --- | --- |
| Studio | `/studio` | 剪辑器：时间线、预览、检查器、代码面板 | `motion studio`、`timeline studio`、`project studio` 打开的都是它 |
| Console | `/console` | 素材库管理和项目列表 | 没有命令会打开它，文档也没提。只有在 `project studio` 下素材库才能用，项目列表也只显示当前这一个项目 |
| Preview | `/` | 只能播放的页面 | 没有入口，没有文档，实际只有测试在用 |
| 引擎 SDK | — | 编译、`<valle-player>` 播放组件、导出，不含界面 | Studio 的预览区和 Preview 页用的是同一个播放组件 |

此外：
- **页面全挂、能不能用看上下文。** 不管哪条命令启动，服务器都挂着所有页面和路由，具体能不能用取决于启动时带了什么。
- **三种会话，保存语义各不相同。** Studio 的三种会话界面相同：
  - 打开 `.tsx` 时，保存写回源码，排列只能另存为 Timeline；
  - 打开 JSON 时，写回这个文件；
  - 打开 project 时，提交一个修订。
- **外部改动只盯 Timeline 文件。** Timeline 文件每 300 毫秒比对一次。它引用的组件文件被改了，Studio 收不到通知；只有打开单个组件时才会监听源文件。
- **Studio 里加不了素材。** 只能给已有的别名换文件，既不能拖入，也不能选择文件。

### 规划

**只保留一个 App：Studio。** 引擎 SDK 不动。

1. **页面**：服务器只提供 Studio，地址就是根路径 `/`。Preview 不再作为页面提供，只留给测试。Console 的两项功能并进 Studio 后，删除 Console。
2. **入口命令**：保留 `motion studio FILE`、`timeline studio FILE` 和 `project studio`，它们和各自的 check、render 是同一套写法和参数。三条命令打开的是同一个 Studio，区别只在打开什么。
3. **会话**：只剩两种，保存时都是写磁盘上的文件。源码和 Timeline 各自沿用现有的保存协议，在项目里时共用项目锁。
   - 组件：一个 `.motion.tsx`。
   - Timeline：一个 JSON。如果它是项目的入口 Timeline，就显示项目名，并启用项目面板（历史和导出）。
   - 项目里的其它 Timeline：只显示项目名和素材面板。快照和导出记录只覆盖入口 Timeline 用到的输入，所以不显示历史和导出面板，免得误操作到入口 Timeline 上。导出用文件模式现有的浏览器导出，不存快照，也不写导出记录。
   - project 会话在第一部分已经删除。
4. **新增面板**：每个面板用的都是和 CLI 相同的原语。
   - **首页**：在项目外运行 `project studio` 时打开，列出最近项目，可以新建项目。最近项目记在 `~/.valle/recent-projects.json`，由项目命令维护。
   - **素材面板**：
     - 浏览项目的 `media/` 和 `components/`，以及素材库：按目录和类型浏览、搜索，改标签和备注，试听试看，查看字体样张。
     - 把文件拖进来等于 `project add`，从素材库拖过来也一样；拖到时间线上，就同时建好资源和片段（组合操作，规则见第 7 条）。
     - 预览素材库里的素材时，带时间的备注标在预览的时间轴上。备注不带进项目，片段上不显示。
   - **历史面板**：快照列表、存快照和恢复，分别对应 history、save、restore。
   - **导出面板**：`renders/` 列表和导出按钮，对应 render。
5. **监听**：范围扩大到 Timeline 引用的组件和媒体。没有未保存的修改时自动重载，有的话提示冲突。
6. **单个组件**：打开 `.tsx` 时的"Save as Timeline"改成"存为项目"，即新建一个项目，并把这个组件放进时间线。这会改变现有行为，属于设计选择。
7. **接口**：Studio 和 CLI 共用同一套原语和校验，返回同样的 JSON。接口沿用现在素材库那种"动词加参数"的形式，每个领域一个入口。
   - Studio 可以把几个原语组合成一次交互，不必为每个按钮加一条命令，但组合操作要写明顺序、失败和撤销。
   - 例如拖到时间线：先 `project add`，它可以重复执行，单个文件失败时它自己什么都没变。拖入多个文件时，只要有一个失败就不改 Timeline，并提示哪些失败了。全部成功后，再按 Timeline 的保存协议写入修改。部分文件失败、修改冲突或校验失败时，已复制的文件留在原处：它没被引用，没有害处，重试时直接复用。撤销只撤 Timeline 的修改，不删文件。

**删除**：Console 应用和 `/console`、Preview 的入口、旧的素材库桥接代码。只为 project 会话存在的前端代码和测试，在第一部分已经删除。

### 取舍

- **一个 App，而不是编辑器加独立的管理页。** 剪辑软件都把素材和项目管理放在编辑器里，用户只需要记一个地址。代价是 Studio 多了几个面板：素材面板可以搬一部分 Console 现有的代码，首页、历史、导出和组合操作都是新做的。
- **保留三条领域命令，不另加 `valle studio`。** 它们和 check、render 是同一套语法，agent 少记一种写法；背后是同一个 App，也不增加维护成本。
- **Studio 和 CLI 共用原语，不是一个按钮一条命令。** 人和 agent 看到的结果一样，校验只有一套。组合操作只在 Studio 里，要用浏览器交互测试单独覆盖。代价是 Web 接口是通用的动词调用，不按 REST 风格设计。
- **Preview 只留给测试。** Studio 的预览区已经有专注模式，看片不需要另一个页面；而测试仍需要一个不带界面的播放页。
- **用"存为项目"替换"Save as Timeline"。** 项目成为排列的唯一归宿。代价是只做单个组件的用户，也要多出一个项目目录。

### 暂不做

- 扩展 Studio 的可视化编辑能力（沿用能力规划里的决定）
- 多人协作
- 云端分享和在线预览链接

## 四、顺序和交付

| 部分 | 新增逻辑 | 删除和整理 |
| --- | --- | --- |
| 一、Project | 项目命令；快照、恢复和导出记录；项目锁；组件 import 检查；批量 add 的逐项结果；放宽路径校验 | 删除修订库和 project 会话，约 5k 行，大部分是删除；保留两套保存协议；重写文档 |
| 二、Assets | 扫描对齐（新文件、按文件号和内容认回、缺失）；文件和数据库的固定先后；重名和并发写入；各平台的废纸篓；用户数据和派生数据分表；管理目录 `.valle/`；保留 7 份的每日备份、`recover` 和损坏处理 | 删掉约 6k 行源码和 3k 行测试（内置分析、pin/lease、实体等）；保留约 1.5k 行数据库和搜索代码并精简；和 CLI 对齐；收拢缓存 |
| 三、Web | 首页、素材、历史、导出四个面板；组合操作；扩大监听范围和冲突界面 | 删除 Console 应用和 Preview 入口；Console 里还能用的界面代码搬进 Studio |

删除的规模是按现有代码统计的。新增逻辑都不小，这里不估行数，每一部分开工前再细估。

每个部分都按下面的要求交付：

- **提交顺序**：先做命令和后端，再做前端。每个提交单独都能通过 CI。
- **验收**：用一条完整流程验收：CLI 建项目 → Studio 添加素材 → agent 修改源码 → Studio 更新 → 导出 → 恢复快照 → 移动项目后重新打开。每部分跑它涉及的那一段：
  - 第一部分：CLI 建项目和 add → agent 改 Timeline 和组件 → 文件模式的 Studio 看到 Timeline 的更新（组件改动的自动重载在第三部分）→ 导出 → 恢复 → 移动项目后重新打开并渲染；
  - 第二部分：加上素材库：入库、在 Finder 里改名（包括有重复内容时）和删除、搜索、放进项目、从备份恢复；
  - 第三部分：全程走 Studio 的面板。
- **平台**：大小写、克隆、废纸篓、文件号、带空格的路径，都要在 Linux 和 Windows 的 CI 里有测试，三个平台都已经有 CI。Mac 上按 CI 的步骤全部跑一遍。
- **中断**：不做杀进程的专门测试。素材库命令中途退出留下的状态，和在 Finder 里新增、改名的结果一样，由扫描的测试覆盖；restore、`project add` 和 `assets add` 测重跑的结果一致。
- **备份恢复**：`recover` 测两种情况：当前数据库损坏时照样能列出和换回备份；旧的 `-wal` 不会套到换回来的数据库上。
- **浏览器交互测试**：Studio 的面板和组合操作要在浏览器里做交互测试，后端测试不能代替。
- **测试**：过时的测试直接删除，也不保留不稳定的测试。CI 的测试清单同步修改。
- **文档**：project、assets、media、cli、timeline 文档和 agent skill 一起修改。

## 五、会改变行为的决定

下面几条会改变现有行为或去掉现有能力。1–5 已于 2026-10-23 确认；6–8 是第 4 版按评审补充的，同日同意写入；第 7 条在第 10 版改为只警告，2026-10-24 同意。其余各项都只是整理。

1. **旧项目和旧素材库都不迁移。** `~/.valle/projects` 里的项目直接作废；`~/.valle/assets` 如果还是旧格式，新命令会报错，提示先把它移走。
2. **完整导出自动存快照。** 每个交付物都能追溯到源文件，内容没变时复用上一个快照。
3. **素材库重做。** 用库内路径代替 sha256 ID；保留 SQLite 和带时间的备注；去掉内置分析、实体、pin/lease 和引用外部文件。VLM 批处理、免模型的镜头检测和素材库里的节拍检测随之去掉。
4. **"Save as Timeline"改成"存为项目"。** 排列统一归到项目里。
5. **动词沿用 create、show、history、restore、render、studio，`show` 改为显示项目概况。** `show` 原来是导出 Timeline，现在 Timeline 本身就是文件，导出已经没有必要。
6. **Timeline 的本地路径允许空格和冒号。** 只有带 `协议://` 的值按 URL 校验，本地路径只拒控制字符。现在会被拒的这类路径都会变成合法。
7. **导出期间媒体变了只警告，不报错。** 成片和导出记录本来就一致，因为渲染读的是导出开始时冻结的副本。发布前再比一次用到的媒体原文件，先比文件身份，身份变了再比摘要；变了就在结果和导出记录里给出警告，提示这个成片以后可能无法从项目完整复现，成片照常交付。
8. **素材库不再自动删表重建。** 结构对不上或数据库损坏时报错停下；用户数据永不自动删除；扫描发现文件不见了，只标成缺失，不删备注。
